# v0.5 — `require`, `remove`, mises à jour partielles

## 1. Cadrage

**Problème.** Depuis 0.4.0, `vivace update` résout tout `composer.json` et
écrit le même lock que Composer. Il manque les trois commandes qui font
évoluer un projet au quotidien : `composer update vendor/name` (partielle),
`composer require`, `composer remove`. Toutes trois reposent sur la même
brique : une mise à jour **partielle**, où les paquets non listés restent
verrouillés à la version du lock.

**Contrainte.** Même promesse que 0.4 : `composer.json` et `composer.lock`
identiques à l'octet à ce que Composer 2.10.3 écrit. Pour `require`, cela
inclut l'édition de `composer.json` **sans en changer la mise en forme**
(Composer édite le texte avec `JsonManipulator`, pas en ré-encodant), et le
choix de la contrainte `^x.y` quand l'utilisateur n'en donne pas.

**Non-objectifs.** `--dry-run`, les questions interactives (Composer
n'interroge pas en `--no-interaction`, c'est le mode de vivace), `--with`
(contraintes temporaires ; la plomberie existe dans `RepositorySet`, la
commande viendra après), `--lock` / `--minimal-changes` /
`update-with-minimal-changes` / `--patch-only` / `--root-reqs`, l'audit,
la recherche de paquets similaires (`levenshtein` sur l'API search), les
messages de `Problem` (R5, toujours reportés : un ensemble insoluble
échoue avec le bon code de retour et un message court). **Refusés
explicitement** quand ils changeraient les octets : `bump-after-update`
(config ou option — Composer lance `bump` après l'update et réécrit
`composer.json` ; port à part, plus tard), `update-with-minimal-changes`.

**Filtre de sécurité du pool.** Composer 2.10.3 retire par défaut du pool
toute version non-dev visée par un avis de sécurité (`policy` vrai,
`SecurityAdvisoryPoolFilter`, sauf paquets verrouillés), désactivable par
`--no-blocking` / `COMPOSER_NO_BLOCKING=1`. vivace ne le porte pas encore :
il se comporte comme `COMPOSER_NO_BLOCKING=1`. La capture des instantanés
tourne avec cette variable pour que live == rejeu, HANDOVER le dit, et le
port (avis capturés dans l'instantané via `security-advisories.api-url`)
est le jalon P7, avant 0.5.0.

**Critères de succès observables.**
1. Oracle « étapes » : pour des fixtures avec un état de départ et une liste
   de commandes (`update x`, `update x -w`, `require x`, `require x:^2`,
   `require --dev x`, `remove x`), `composer.json` et `composer.lock` après
   chaque étape sont identiques à l'octet entre Composer et vivace, sur un
   instantané Packagist figé. Six scénarios au moins, en CI.
2. Oracle du pool en mise à jour partielle : `tools/oracle-pool.php
   --update a/b [--with-dependencies]` — pool, décisions, opérations et lock
   identiques (la machinerie `skippedLoad`/`unlock` de `PoolBuilder`,
   portée en R1 sans oracle, est exercée ici).
3. Oracle `JsonManipulator` : un corpus de `composer.json` réels et
   synthétiques (indentation à 2/4 espaces et tabulations, clés absentes,
   sections vides, tri `sort-packages`, commentaires impossibles mais
   valeurs exotiques) passé par le phar et par le port, sortie identique.
4. Oracle `VersionSelector` : pour chaque paquet des instantanés, la
   contrainte recommandée (`findRecommendedRequireVersion`) et le candidat
   choisi (`findBestCandidate` avec la plateforme locale) identiques.

## 2. Ce que fait Composer (lu dans les sources vendorées)

- **Partielle** (`UpdateCommand` → `Installer::setUpdateAllowList`,
  `setUpdateAllowTransitiveDependencies`) : liste en minuscules dédoublonnée
  ; sans lock → erreur « Cannot update only a partial set of packages
  without a lock file present » ; `PoolBuilder` verrouille les paquets du
  lock hors liste (`lockPackage`), les débloque de proche en proche selon
  le mode (`UPDATE_ONLY_LISTED` / `…NO_ROOT_REQUIRE` / `…WITH_TRANSITIVE_DEPS`),
  avertit sur les motifs sans correspondance. `Installer::setUpdateAllowList`
  refuse `--with` et les motifs vides.
- **`require`** (`RequireCommand`) : `parseNameVersionPairs` (paire
  `nom[:= ]contrainte`, ou deux arguments quand le second n'a pas de `/`
  et n'est pas un nom de plateforme), avertissement sur `1.2` trop strict ;
  la casse des noms est conservée telle que tapée. Sans contrainte,
  `findBestVersionAndNameForPackage` tourne **toujours** (validation :
  paquet introuvable, plateforme incompatible, stabilité ; et le nom
  devient `getPrettyName()`) ; ensuite, avec `--no-update`, la contrainte
  calculée (`findRecommendedRequireVersion`) est écrite tout de suite ;
  sinon (`--fixed` compris) c'est `guess` : on requiert `*`, **une seule
  résolution** par le solveur, puis `updateRequirementsAfterResolution`
  prend le paquet verrouillé (`getPrettyVersion` si `--fixed`, sinon
  `^x.y`) — un paquet de plateforme (`php`, `ext-*`) n'est pas dans le
  lock et garde `*` — réécrit `composer.json`, et `Locker::updateHash`
  relit le lock, remplace `content-hash` en place, ajoute les
  `stability-flags` devinés (jamais n'en retire), `fixupJsonDataType`, et
  réécrit avec l'indentation détectée à la lecture, seulement si les
  octets changent et seulement si `doUpdate` a rendu 0. Refus : requérir la
  racine, contrainte invalide, clé incohérente (`require` ↔ `require-dev`)
  → en non-interactif, avertissement et on continue (le paquet est déplacé).
  Édition : `JsonManipulator::addLink` (+ tri), `removeSubNode` de l'autre
  clé, `removeMainKeyIfEmpty` ; repli `JsonFile::write` si le manipulateur
  échoue. Puis `Installer` en update avec liste = paquets requis (sauf
  premier `require` d'un manifeste vide, ou sans lock), mode transitif
  selon `-w`/`-W`, `install` sauf `--no-install`. Échec → `composer.json`
  (et lock) restaurés.
- **`remove`** (`RemoveCommand`) : noms en minuscules remappés vers
  l'orthographe du manifeste, motifs `*` autorisés, paquet présent dans
  l'autre clé → avertissement (pas de déplacement en non-interactif),
  `--unused` (paquets non-dev du lock que rien ne requiert),
  `allow-plugins` nettoyé pour les plugins retirés **après** le retour
  `--no-update` et avant l'update (`removeConfigSetting` → `JsonManipulator`
  ré-sérialise tout le bloc `config`), puis update partielle mode
  `…NO_ROOT_REQUIRE` par défaut (`-W` ou `--no-update-with-dependencies` ;
  `COMPOSER_WITH_DEPENDENCIES` est ignoré par `remove`), même quand le
  paquet n'était qu'une dépendance transitive (il peut alors être mis à
  niveau), restauration de `composer.json` seul en cas d'échec, erreur 2
  si le paquet est encore dans `installed.json` (jamais avec `--no-install`).
- **`VersionSelector`** : candidats de `RepositorySet::findPackages` (toutes
  stabilités si demandé), tri stabilité préférée puis `version_compare`
  décroissant, filtre des exigences de plateforme (php, ext-*) contre le
  `PlatformRepository` local, alias `9999999-dev` → paquet aliasé ;
  `transformVersion` : `x.y.z.w` → `^x.y` (`^0.y.z` sous 1.0), `@stability`
  si non stable, branches dev → alias de branche → `^x.y`, sinon version
  jolie.
- **`JsonManipulator`** : manipulation textuelle par expressions
  régulières. Périmètre réellement atteint par `require`/`remove` :
  constructeur (`trim` + un seul `\n` final, `\r\n` détecté,
  `detectIndenting` = première ligne `^[ \t]+"`), `addLink` (existant :
  regex insensible à la casse, orthographe existante conservée, contrainte
  insérée brute ; section absente → `addMainKey` en fin de fichier ;
  section vide `{}` → construite ; `sortPackages` → `strnatcmp` sensible à
  la casse et reformatage complet de la section par `format`),
  `removeSubNode` (`isset` sensible puis regex insensible ; repli
  `JsonFile::write` sur `PREG_BACKTRACK_LIMIT_ERROR`), `addSubNode`,
  `removeMainKey`, `removeMainKeyIfEmpty`, `removeConfigSetting`, `format`.
  Le reste (`repositories`, listes, `addProperty`) n'est pas porté. Fichier
  absent ou vide → `{\n}\n`.

## 4. Risques
- **`JsonManipulator` est le port le plus exposé** : sa fidélité se juge
  au caractère près sur des entrées variées ; un corpus réel (les
  `composer.json` des fixtures et des paquets des instantanés, qui sont des
  manifestes de bibliothèques) est indispensable.
- **`guess` → deux résolutions** : la seconde passe (`updateHash`) touche
  le lock existant sans le régénérer ; la moindre différence de
  ré-encodage se verrait — l'oracle à étapes la couvre.
- **Verrouillage partiel** : le port de `unlockPackage`/`skippedLoad` n'a
  jamais tourné ; c'est P1, avant tout le reste, avec l'oracle des
  décisions.
- **Effets de bord de Composer non reproduits** : les avertissements
  (« Pattern … does not match any locked packages », « Dependency … is
  also a root requirement ») sont du texte sur stderr ; ils sont portés
  mais pas comparés.

## 5. P7 — politiques de blocage du pool (cadrage, 2026-09-14)

### Problème

Composer 2.10 retire du pool, **avant l'optimiseur**, les versions que ses
politiques bloquent (`PoolBuilder::buildPool` : `runSecurityAdvisoryFilter`
puis `runFilterListFilter` puis `runOptimizer`) :

1. **Avis de sécurité** (`policy.advisories.block`, défaut vrai) : toute
   version non-dev d'un paquet ni racine, ni plateforme, ni verrouillé
   (`Request::isLockedPackage`) dont une des `getNames(false)` (nom +
   `replace`) a un avis dont `affectedVersions` accepte la version.
2. **Listes de filtrage** (`policy.malware.block`, défaut vrai ; listes
   personnalisées) : toute version d'un paquet ni racine ni plateforme
   dont une entrée de liste active accepte la version ; les versions
   verrouillées (ou identiques à une version du lock) sont jugées contre
   les listes de portée *install* (la liste malware la supporte) — un
   paquet verrouillé sur une version malveillante est donc retiré même en
   mise à jour partielle.
3. **Abandonnés** (`policy.abandoned.block`, défaut faux).

Et `composer install` lui-même (`Installer::doInstall`) passe le pool du
lock par le filtre de listes en portée *install* : une version malveillante
verrouillée n'est pas installée. vivace ignore les trois filtres et
n'inspecte rien à l'installation — l'équivalent de `--no-blocking`, que le
harness pose des deux côtés depuis 89195cb. Écart observable (et de
sécurité) : quand la meilleure version acceptable est vulnérable ou
signalée, Composer en choisit une autre ou échoue, vivace la retient.

### Ce que Packagist fournit (lu dans les sources et sur le dépôt)

- `packages.json` : `security-advisories: {metadata: true, api-url:
  https://packagist.org/api/security-advisories/}` et `filter: {metadata:
  true, lists: {malware: {enabled: true}}, summary-url:
  https://repo.packagist.org/lists/all/summary.json}`.
- Avec `metadata: true`, chaque fichier `p2/vendor/name.json` porte
  `security-advisories: [{advisoryId, affectedVersions}]` (avis
  **partiels** — les instantanés les contiennent déjà, 136/136 fichiers de
  Laravel) et, pour un paquet signalé, `filter: {malware: [{constraint,
  url, reason, id, source}]}` (vérifié sur `bfunky/http-parser`).
- L'API `api-url` (POST `packages[]`) ne sert qu'au chargement **complet**
  (`Auditor::needsCompleteAdvisoryLoad` : règles d'ignorance par
  identifiant non `PKSA-` ou par sévérité). Le résumé `summary.json`
  (`filter.malware: {name: "contrainte|contrainte"}`, cache 600 s) sert à
  ne relire que les fichiers p2 des candidats signalés.
- Un dépôt sans ces clés (les `packages.json` réécrits par le harness et
  les oracles) : `securityAdvisoryConfig`/`filterConfig` nuls, filtres
  sans effet — c'est pourquoi `COMPOSER_NO_BLOCKING` n'a jamais changé un
  lock du harness.

  `COMPOSER_POLICY_MALWARE_BLOCK`, `COMPOSER_POLICY_ABANDONED_BLOCK` /

  packageNamesToRegexp` — ou par identifiant `PKSA-…` disponible en
  partiel), `policy.malware.{block, ignore, ignore-source}`,
  `policy.abandoned.{block, ignore}`, `policy.ignore-unreachable`, config
  globale fusionnée (`Config::merge` : `policy` est un tableau fusionné
  récursivement ? — à vérifier dans `Config::merge`).
- **Refusés explicitement** (message, code 1) plutôt que divergents :
  `policy.advisories.ignore-severity`, ignorance par identifiant non
  `PKSA-` (chargement complet via l'API, non porté), listes personnalisées
  (`policy.<autre>`), un dépôt dont `filter.api-url` est défini.
- **Avis** : `RepositorySet::getMatchingSecurityAdvisories` (contraintes
  `=` par nom, alias racine exclus, `MultiConstraint` disjonctive),
  `ComposerRepository::getSecurityAdvisories` chemin métadonnées
  (`hasAvailablePackageList` → `lazyProvidersRepoContains`, fichiers p2
  déjà chargés ou lus par le cache), `PartialSecurityAdvisory::create`
  (`affectedVersions` par `parseConstraints`), `Auditor::processAdvisories`
  pour la liste d'ignorance, `SecurityAdvisoryPoolFilter::filter` avec la
  règle `getNames(false)` (un avis sur un paquet remplacé ne compte que si
  ce paquet est lui-même dans le pool, puisque la requête ne porte que sur
  `getName()`).
- **Listes** : `ComposerRepository::getFilter` chemin résumé + p2,
  `FilterListEntryBuilder`, `FilterListAuditor::matchingEntries`
  (ignorance par paquet/contrainte, `ignore-source`), `FilterListPoolFilter`
  avec `blockScope` update et la règle des versions verrouillées ; et le
  **passage du pool du lock en portée install dans `vivace install`**
  (échec avec le message de Composer si une version verrouillée est
  signalée).
- **Abandonnés** : `Auditor::filterAbandonedPackages` (`abandoned` du
  paquet, liste d'ignorance), actif seulement si `block` vrai.
- Les `securityRemovedVersions`/`filterListRemovedVersions` ne servent
  qu'aux explications d'un ensemble insoluble (non portées) : pas gardés.
  Les messages sont en VERY_VERBOSE chez Composer : rien à afficher.

### Risques

- Composer relit `summary.json` avec un TTL de 600 s dans son cache : hors
  ligne au-delà, `ignore-unreachable` décide (défaut : erreur). Le port
  doit reproduire le cache (`cache-repo-dir`, clé de fichier) pour que
  `--offline` et les tests se comportent pareil.
- Les instantanés existants n'ont pas de `summary.json` : ils seront
  rejoués avec un résumé vide (aucun paquet signalé, ce qui est vrai pour
  ces cinq projets au moment de la capture) — à recapturer à la prochaine
  occasion.
- `Config::merge` pour `policy` et `audit` : vérifier si le tableau projet
  remplace ou fusionne le global (impact sur `ignore`).

### Méta (sous-agent frais, 2026-09-14) — ce qui change

Quinze points, vérifiés dans les sources et par rejeu des cinq instantanés
avec les politiques activées (`available-package-patterns: ["*"]` +
`api-url: null` : locks identiques, pools réduits de 2 à 23 %).

1. **`filterListRemovedVersions` pilote le solveur** : `RuleSetGenerator`
   n'émet pas de règle FIXED pour un verrouillé retiré par une liste, et
   `Solver::checkForFilterListRemovedLockedPackages` crée un problème
   `RULE_LOCKED_FILTER_LIST_REMOVED` (« Package X vY (in the lock file) was
   not loaded, because it was flagged as malware … »), code 2. À porter
   (`Pool.filter_list_removed`, `rules_gen`, `solver`). Les
   `securityRemovedVersions` ne servent qu'aux explications : non portés.
2. **La config héritée `audit.*` est le chemin par défaut** (`Config`
   défaut `audit: {ignore: [], abandoned: fail}`) : `audit.block-insecure`,
   `audit.ignore` (ids et noms mélangés), `audit.ignore-severity`,
   `audit.block-abandoned`, `audit.ignore-abandoned`,
   `audit.ignore-unreachable` entrent au périmètre, plus `COMPOSER_POLICY`
   (`0` désactive tout), `policy.malware.block-scope` (`all`/`update`/
   `install`), l'option `repositories.x.filter`, la clé `ignore-id`, et la
   sémantique de `Platform::getBoolEnv` (`false`/`off`/`0` faux, valeur
   invalide → erreur). Fusion global/projet : `array_merge` par liste,
   `false` gagne, listes `ignore*` concaténées.
3. **Toute ignorance d'avis (par nom aussi) force le chargement complet
   via `api-url`** (`needsCompleteAdvisoryLoad` teste chaque clé) ; sans
   API, Composer plante (exit 1). Et un projet multi-dépôts ou un nom sans
   p2 (404) part aussi en POST. Décision : **porter le POST**
   (`Content-type: application/x-www-form-urlencoded`, `packages[]`,
   timeout 10 s, avertissement sur les noms non demandés), exercé contre
   Packagist en direct par un test hors CI ; hors ligne, `ignore-unreachable`
   (défaut **vrai** en install et update : avertissement, pas erreur ; à
   `false` : code 100) décide.
4. **Ignorance des avis par nom = égalité exacte** (`array_key_exists`),
   pas motif ; motifs + contraintes pour les listes, motifs seuls pour les
   abandonnés. Les abandonnés sont retirés **dans** le filtre d'avis (donc
   éteints avec lui), sur tous les paquets du pool. Les listes filtrent
   aussi les versions dev ; les avis non.
5. **Fixture** : `api-url: null` exige `available-package-patterns` ;
   un ensemble insoluble à cause d'un avis partiel fait planter Composer
   (rechargement complet pour l'explication) → embarquer des avis
   **complets** (`title`, `sources`, `reportedAt`) dans les p2 de la
   fixture ; l'exemple guzzle était faux (tout 7.4.* est vulnérable),
   prendre une contrainte à borne haute saine ou des avis fabriqués.
6. **Résumé et cache** : `summary.json` n'est lu que si aucun fichier de
   métadonnées n'a été chargé dans le processus (`freshMetadataUrls === []`)
   — donc jamais en `update`, seulement en `install` ; clé de cache
   `filter-summary.json`, `If-Modified-Since`, sans TTL ; `packages.json`
   a un TTL de 600 s en `install`. `PartialSecurityAdvisory::create` a
   deux replis sur contrainte invalide ; une entrée de liste invalide est
   une exception.
7. **`vivace install`** : charger les `packages.json` des dépôts, le
   résumé, les p2 des candidats, filtrer les paquets du lock (alias
   inclus) contre la liste malware en portée install, et échouer avec
   « Your lock file does not contain a compatible set of packages. Please
   run composer update. » + les problèmes, code 2.

Ordre d'exécution : (A) `policy.rs` (config + env + fusion), (B) avis
(p2 partiels, POST, `PartialSecurityAdvisory`, `processAdvisories`, filtre
+ abandonnés), (C) listes (p2, résumé, `FilterListEntry`, `matchingEntries`,
`block-scope`, verrouillés, `Pool.filter_list_removed`, règles et problème
du solveur), (D) passage install, (E) instantanés/harness/oracle/fixture.
