# v0.5 — `require`, `remove`, mises à jour partielles

## 1. Cadrage

**Problème.** Depuis 0.4.0, `vivace update` résout tout `composer.json` et
écrit le même lock que Composer. Il manque les trois commandes qui font
évoluer un projet au quotidien : `composer update vendor/name` (partielle),
`composer require`, `composer remove`. Toutes trois reposent sur la même
brique : une mise à jour **partielle**, où les paquets non listés restent
verrouillés à la version du lock.

**Contrainte.** Même promesse que 0.4 : `composer.json` et `composer.lock`
identiques à l'octet à ce que Composer 2.10.3 écrit. Pour `require`, cela
inclut l'édition de `composer.json` **sans en changer la mise en forme**
(Composer édite le texte avec `JsonManipulator`, pas en ré-encodant), et le
choix de la contrainte `^x.y` quand l'utilisateur n'en donne pas.

**Non-objectifs.** `--dry-run`, les questions interactives (Composer
n'interroge pas en `--no-interaction`, c'est le mode de vivace), `--with`
(contraintes temporaires ; la plomberie existe dans `RepositorySet`, la
commande viendra après), `--lock` / `--minimal-changes`, l'audit, la
recherche de paquets similaires (`levenshtein` sur l'API search), les
messages de `Problem` (R5, toujours reportés : un ensemble insoluble
échoue avec le bon code de retour et un message court).

**Critères de succès observables.**
1. Oracle « étapes » : pour des fixtures avec un état de départ et une liste
   de commandes (`update x`, `update x -w`, `require x`, `require x:^2`,
   `require --dev x`, `remove x`), `composer.json` et `composer.lock` après
   chaque étape sont identiques à l'octet entre Composer et vivace, sur un
   instantané Packagist figé. Six scénarios au moins, en CI.
2. Oracle du pool en mise à jour partielle : `tools/oracle-pool.php
   --update a/b [--with-dependencies]` — pool, décisions, opérations et lock
   identiques (la machinerie `skippedLoad`/`unlock` de `PoolBuilder`,
   portée en R1 sans oracle, est exercée ici).
3. Oracle `JsonManipulator` : un corpus de `composer.json` réels et
   synthétiques (indentation à 2/4 espaces et tabulations, clés absentes,
   sections vides, tri `sort-packages`, commentaires impossibles mais
   valeurs exotiques) passé par le phar et par le port, sortie identique.
4. Oracle `VersionSelector` : pour chaque paquet des instantanés, la
   contrainte recommandée (`findRecommendedRequireVersion`) et le candidat
   choisi (`findBestCandidate` avec la plateforme locale) identiques.

## 2. Ce que fait Composer (lu dans les sources vendorées)

- **Partielle** (`UpdateCommand` → `Installer::setUpdateAllowList`,
  `setUpdateAllowTransitiveDependencies`) : liste en minuscules dédoublonnée
  ; sans lock → erreur « Cannot update only a partial set of packages
  without a lock file present » ; `PoolBuilder` verrouille les paquets du
  lock hors liste (`lockPackage`), les débloque de proche en proche selon
  le mode (`UPDATE_ONLY_LISTED` / `…NO_ROOT_REQUIRE` / `…WITH_TRANSITIVE_DEPS`),
  avertit sur les motifs sans correspondance. `Installer::setUpdateAllowList`
  refuse `--with` et les motifs vides.
- **`require`** (`RequireCommand`) : `parseNameVersionPairs` (paire
  `nom[:= ]contrainte`, ou deux arguments quand le second n'a pas de `/`),
  avertissement sur `1.2` trop strict ; sans contrainte → `guess` : on
  requiert `*`, on résout, puis `findRecommendedRequireVersion` sur le
  paquet verrouillé réécrit `composer.json` et `Locker::updateHash` remet
  `content-hash` et `stability-flags` dans le lock ; avec `--no-update` ou
  `--fixed` → `findBestCandidate` tout de suite. Refus : requérir la
  racine, contrainte invalide, clé incohérente (`require` ↔ `require-dev`)
  → en non-interactif, avertissement et on continue (le paquet est déplacé).
  Édition : `JsonManipulator::addLink` (+ tri), `removeSubNode` de l'autre
  clé, `removeMainKeyIfEmpty` ; repli `JsonFile::write` si le manipulateur
  échoue. Puis `Installer` en update avec liste = paquets requis (sauf
  premier `require` d'un manifeste vide, ou sans lock), mode transitif
  selon `-w`/`-W`, `install` sauf `--no-install`. Échec → `composer.json`
  (et lock) restaurés.
- **`remove`** (`RemoveCommand`) : noms en minuscules, motifs `*` autorisés,
  paquet présent dans l'autre clé → avertissement (pas de déplacement en
  non-interactif), `--unused` (paquets du lock que rien ne requiert),
  `allow-plugins` nettoyé pour les plugins retirés, puis update partielle
  mode `…NO_ROOT_REQUIRE` par défaut (`-W` ou `--no-update-with-dependencies`),
  restauration en cas d'échec, erreur 2 si le paquet est encore installé.
- **`VersionSelector`** : candidats de `RepositorySet::findPackages` (toutes
  stabilités si demandé), tri stabilité préférée puis `version_compare`
  décroissant, filtre des exigences de plateforme (php, ext-*) contre le
  `PlatformRepository` local, alias `9999999-dev` → paquet aliasé ;
  `transformVersion` : `x.y.z.w` → `^x.y` (`^0.y.z` sous 1.0), `@stability`
  si non stable, branches dev → alias de branche → `^x.y`, sinon version
  jolie.
- **`JsonManipulator`** : 1 084 lignes de manipulation textuelle par
  expressions régulières (détection de l'indentation, insertion en fin de
  section, tri optionnel, suppression de nœud avec gestion des virgules et
  lignes vides). À porter tel quel avec les mêmes PCRE.

## 3. Plan

| jalon | livrable | oracle |
|---|---|---|
| P1 | `vivace update [pkg…] [-w|-W]` : liste d'autorisation, modes, avertissements ; `Installer` (`setUpdateAllowList`) et CLI | `tools/oracle-pool.php --update` étendu ; `tools/snapshot-packagist.sh` apprend les fixtures « à étapes » ; `harness/update.sh` rejoue les étapes |
| P2 | `crates/vivace-resolver/src/json_manipulator.rs` : port de `JsonManipulator` (`addLink`, `removeSubNode`, `removeMainKeyIfEmpty`, `addMainKey`, `addSubNode`, `removeMainKey`, `addProperty/removeProperty` pour `config`) | `tests/oracle_json_manipulator.rs` : corpus vs phar |
| P3 | `version_selector.rs` : `findBestCandidate`, `findRecommendedRequireVersion` ; `RepositorySet::find_packages` | `tests/oracle_version_selector.rs` : tous les paquets des instantanés |
| P4 | `vivace require` : arguments, `guess`, édition, update partielle, `updateRequirementsAfterResolution` + `Locker::updateHash`, restauration | fixtures à étapes |
| P5 | `vivace remove` : arguments, motifs, `--unused`, `allow-plugins`, update partielle, restauration | fixtures à étapes |
| P6 | docs, CHANGELOG, HANDOVER (miroirs incohérents, `--with`), 0.5.0 | CI verte |

Fixtures à étapes (`fixtures/projects/steps-*/`) : `composer.json` +
`composer.lock` de départ (petits, quelques paquets, pour garder les
instantanés légers) et `STEPS` (une commande par ligne). Le script
d'instantané rejoue les étapes avec Composer sur Packagist, cache vide,
et range dans l'archive : les fichiers p2 touchés, et pour chaque étape
`expected/<n>/composer.json` + `composer.lock`. Le test Rust rejoue avec
vivace sur l'instantané et compare après chaque étape.

## 4. Risques
- **`JsonManipulator` est le port le plus exposé** : sa fidélité se juge
  au caractère près sur des entrées variées ; un corpus réel (les
  `composer.json` des fixtures et des paquets des instantanés, qui sont des
  manifestes de bibliothèques) est indispensable.
- **`guess` → deux résolutions** : la seconde passe (`updateHash`) touche
  le lock existant sans le régénérer ; la moindre différence de
  ré-encodage se verrait — l'oracle à étapes la couvre.
- **Verrouillage partiel** : le port de `unlockPackage`/`skippedLoad` n'a
  jamais tourné ; c'est P1, avant tout le reste, avec l'oracle des
  décisions.
- **Effets de bord de Composer non reproduits** : les avertissements
  (« Pattern … does not match any locked packages », « Dependency … is
  also a root requirement ») sont du texte sur stderr ; ils sont portés
  mais pas comparés.
