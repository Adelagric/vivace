# v0.8 — `--dry-run`, the operation lines, `path` repositories

Decided on 2026-09-15 after the 0.7.0 release ("On v0.8 pour le moment").

## 1. Scope

### Problem

1. `vivacity update`/`require`/`remove --dry-run` are refused. In
   Composer a dry run resolves, prints what it would do and writes
   nothing — the way people preview an update in CI or before a risky
   bump.
2. Composer's `update` prints one line per lock operation
   (`  - Locking acme/a (1.2.0)`, `  - Upgrading acme/b (1.0.0 => 1.1.0)`,
   `  - Removing acme/c (2.0.0)`), always, in name order; vivacity prints
   the `Lock file operations:` summary only. That is a stderr divergence
   on every successful update, never measured because the harness only
   compared the lock. A dry run without these lines is pointless.
3. `path` repositories (`{"type": "path", "url": "../lib"}`, monorepos,
   local development of a library) are refused by `update` and their
   packages are out of scope for `install` (no zip dist → fallback).
   They are the most common repository type after `composer`.

### Constraints

- Byte-identical stderr (`--no-ansi` rendering) and files with Composer
  2.10.3, proven by the differential harnesses; every ported file
  vendored under `docs/reference/` (`drift-reference.sh`).
- No new dependency without a DECISIONS entry.
- The `path` install must respect `transport-options.symlink`,
  `COMPOSER_MIRROR_PATH_REPOS`, and produce the same `vendor/` as
  Composer (a symlink or a mirrored copy), on Linux/macOS; Windows
  junctions are out of the parity claim (documented, like the rest of
  the Windows port).

### Non-goals

- `vcs` repositories (git driver, GitHub/GitLab API drivers, source
  installs by `git clone`): a version of their own (v0.9). Their packages
  keep going through the fallback; a `vcs` repository in `update` keeps
  being refused with the current message.
- `bump-after-update`, `--minimal-changes`, `--with` (unchanged).
- `install --dry-run` beyond what exists (policy/platform checks): the
  "Package operations" listing of `doInstall` for `install`/`update
  --dry-run` without `--no-install` — see P4: it is in scope for the
  lines the lock step prints; the install step's listing is in scope
  only as far as `Installing`/`Upgrading`/`Removing` lines from the
  lock→installed diff, which vivacity computes already for the real
  install.
- The interactive prompt of `remove` (non-interactive behaviour kept).

### Assumption stated (the user chose "v0.8" without detail)

The plan of v0.7 listed `--dry-run`, `vcs`/`path` repositories and
`bump-after-update` for v0.8. `vcs` alone is ~2 000 lines of reference
(VcsRepository, GitDriver, GitHubDriver, GitDownloader) and changes the
install side (source checkouts); it would double this version. `path` is
254 + 335 lines and has no network. Decision: `--dry-run` + operation
lines + `path` now; `vcs` and `bump-after-update` next. Changeable on the
user's word.

### Success criteria (observable)

- D1. `harness/steps.sh` gains `@stderr` success anchors (`Lock file
  operations`, `Nothing to modify in lock file`): on every successful
  `update`/`require`/`remove` case of the corpus (~130 cases), stderr
  from the anchor to the end is byte-identical to Composer's — the
  operation lines, `Writing lock file`, and for `require`/`remove` the
  trailing lines they print.
- D2. `--dry-run` on `update`, `require`, `remove`: same stderr as
  Composer's dry run, exit code identical, **no file changed** (composer.json,
  composer.lock, vendor/) — the harness checks the three are byte-equal
  to their pre-state, on both sides. Cases: full update, partial update,
  `require` new package (file left untouched, "has been updated" still
  printed like Composer), `require` on a project without composer.json
  (created then deleted), `remove`, `--no-install` variants, an
  unsolvable dry run (exit 2, explanations unchanged), `update --dry-run`
  without `--no-install` on an already-installed vendor/ (install-phase
  lines: `Installing dependencies from lock file (including require-dev)`,
  `Package operations: …`, `  - Installing …`/`Upgrading`/`Removing`, then
  nothing written).
- P1. A `path` repository in `update` produces the same lock as Composer:
  packages with `dist: {type: path, url, reference}` (reference = sha1 of
  the directory's composer.json + git HEAD when available — port of
  `PathRepository::initialize`), `version` from `options.versions`, else
  from the package's composer.json, else `VersionGuesser` on the
  directory (git branch/tag), `transport-options` (`symlink`,
  `relative`), glob patterns in `url` (`../packages/*`), `~` and env
  expansion (`Platform::expandPath`). Oracle: `harness/update.sh` on a
  new fixture `path-repos` (a project with two local packages: one with
  `version` declared, one guessed from a git branch, one glob) — lock
  identical; `harness/steps.sh` cases (`require` of a path package,
  `update` with the path package changed).
- P2. `install` of a path package: symlink (default, relative when
  possible — `findShortestPath`) or mirror copy (`symlink: false`,
  `COMPOSER_MIRROR_PATH_REPOS=1`, or when the symlink fails), the
  `installed.json`/`installed.php` entries identical, `vendor/` identical
  (`diff-vendor.sh` on the fixture: symlink target compared, copy
  compared file by file), removal on `remove` (unlink, never the target
  directory's content). Scope detector: a path package is native when
  its `dist.url` resolves to a directory.
- P3. `remove`/`require --dry-run` exit codes and revert semantics
  identical (the "reverting" line is not printed on a dry run since no
  file changed? — to verify against the reference: `RemoveCommand` still
  prints "Removal failed, reverting" on a failed dry run and restores
  the backup, which is a no-op).

## 2. Plan

### Part D — dry run and operation lines

1. **Oracle first.** `steps.sh`: the `@stderr` anchor list gains
   `^Lock file operations`, `^Nothing to modify in lock file`,
   `^Installing dependencies from lock file`; `@stderr` is added to every
   successful case of the table (a case whose reference output has no
   anchor is reported, as today). Expect ~130 red cases. New `@dry`
   marker: appends `--dry-run` to the command and, after both runs,
   checks composer.json/composer.lock/vendor are byte-identical to the
   pre-state on each side (and equal between sides).
2. **Operation lines** (`Installer::doUpdate` after the solve):
   `Operation::show(true)` port (`Locking`, `Upgrading`/`Downgrading`
   with `VersionParser::isUpgrade` and the `getFullPrettyVersion`
   variants — source ref for dev packages, `DISPLAY_SOURCE_REF`/`DIST_REF`
   when versions are equal, `Removing`), `usort` by name with
   `strcmp`, uninstalls first, alias operations skipped (unless debug),
   `<info>`/`<comment>` stripped. Also `Installs:`/`Updates:`/`Removals:`
   are VERBOSE-only: not printed. `config.lock: false` prints none of it.
3. **`update --dry-run`**: `Installer::dryRun` semantics — resolve, print
   the lines, no lock write (`Writing lock file` not printed), no install
   (`--no-install` implied for our purposes? No: without `--no-install`
   Composer runs `doInstall` in dry mode: `Installing dependencies from
   lock file (including require-dev)`, `Package operations: …`, the
   `  - Installing/Upgrading/Removing` lines from the lock vs
   installed.json diff, then `Generating autoload files`? — no: dumpAutoloader
   false. Port: reuse the install plan computation (scope + installer
   plan) without executing; the lines come from the plan's operations
   sorted like Composer (`Transaction` for install — check whether the
   install transaction order is by name or by dependency order:
   `Installer::doInstall` prints `$localRepoTransaction->getOperations()`
   in transaction order, which is dependency order — the existing
   `install` code has that order for its own execution; verify by
   oracle).
4. **`require --dry-run`**: `RequireCommand`: file not written but
   "composer.json has been updated" printed; the root package patched in
   memory with the new links (+ references, stability flags); the
   update runs dry; `updateRequirementsAfterResolution` prints the
   guessed constraints but does not write; a newly created composer.json
   is deleted at the end (`finally`). `require --dry-run --no-update`:
   nothing written, prints "has been updated". Refusal of `--dry-run`
   removed in `require.rs`.
5. **`remove --dry-run`**: links collected instead of removed from the
   file, root package patched in memory, update dry, no `allow-plugins`
   cleanup, no "still present" check; failure prints the "reverting"
   line and restores the backup (no-op).
6. Docs: README (remove `--dry-run` from "not yet"), HANDOVER, CHANGELOG.

   `initialize`: `Platform::expandPath(url)`, `glob()` with
   `GLOB_BRACE|GLOB_MARK|GLOB_ONLYDIR`? (check flags), absolute path

   `{type: path, url: <as written or absolute>, reference: sha1(json +

   → url kept relative), version: `options.versions[name]`, else
   `version` in the json, else `VersionGuesser::guessVersion` (git of the

14. Docs: README ("Repositories: `composer` and `path`"), HANDOVER

## 3. Meta-analysis (adversarial, fresh subagent, 2026-09-15)

14 flaws, 7 major. All accepted. Two of them change the shape of the
version.

### Part D — accepted corrections

- **M3 (major) D2's "no file changed" is false in Composer itself**:
  `RequireCommand` writes `{\n}\n` before any dry-run test when the
  file is missing or empty (`RequireCommand.php:139-152`), and deletes
  it only on the update path (`finally`, `:349`): `require --dry-run
  --no-update` on a missing json leaves the file; on an empty json the
  bytes change and stay. → the harness invariant is `ref == viv` for
  every file plus the exit code; the pre-state check is informative;
  vivacity ports the two writes literally.
- **M4 (major) the tail after `Writing lock file` has three outputs the
  plan never named**: the suggestions count (`outputMinimalistic`, on a
  fresh install with the root's own suggestions, filtered by what the
  platform/locked/root packages provide), one `Package X is abandoned`
  warning per abandoned package of the NEW lock (dev included), and the
  funding line from the installed state. Sylius (root `suggest`, 3
  abandoned locked packages) and `solver-policies` (`acme/abandoned`)
  would fail D1 regardless of the operation lines. → ported, with the
  suggestion filter using the detected extensions.
- **M5 (major) `steps.sh` cannot see the install-phase dry run**
  (`--no-install` hard-coded, no vendor) → a `@dry-install` marker drops
  `--no-install` on both sides with an `@installed:` pre-state, so
  `Installing dependencies from lock file (including require-dev)`,
  `Package operations: …` and the `  - Installing/Upgrading/Removing`
  lines (transaction order, `show(false)`) are compared.
- **M7 (major) `require --dry-run` needs a root patch hook**: the
  session builds the Request and RepositorySet from the on-disk root in
  `prepare_update`; a text shortcut is not equivalent (`array_merge`
  appends the new links unsorted, the file path inserts them sorted →
  different rule order, different problem text on an unsolvable dry
  run). → `RootPatch { links, references, stability_flags }` applied to
  the loaded root; `remove --dry-run` uses it with `unset` only, and
  keeps Composer's quirk (original-cased name unset against lowercase
  keys: a mixed-case manifest key is not removed in a dry run).
- **M8** the dry install listing comes from `Transaction::new(present =
  installed.json, result = new lock)` — the resolver's transaction, not
  the installer's plan order.
- **M11** operation lines of dev packages without a source show the
  dist reference (7 chars of 40), `isUpgrade` treats any `dev-` side as
  an upgrade.
- **M14** Composer audits on every update unless `--no-audit`, dry runs
  included; vivacity does not audit. The harness passes `--no-audit` to
  Composer; the parity claim is scoped to `--no-audit` (documented).

### Part P — moved out of this version

- **M1 (major)** the `dist.reference` formula is
  `sha1($json . serialize($options))` with `relative` auto-appended to
  the options, replaced by the HEAD hash only for a nested `.git` with
  `reference: auto`: a PHP `serialize()` port is needed.
- **M2 (major)** `PathRepository` runs `git` in the package directory
  and lets it walk up to the enclosing repository (every monorepo
  sub-package, and every harness copy since `diff-vendor.sh` commits the
  tree), and adds TWO packages when a feature branch has a parent
  (`dev-feature-x` and `dev-main`): core's root guesser (requires
  `<dir>/.git`, pins `GIT_DIR`, one version) cannot be reused as is.
- **M6 (major)** a nested `.git` cannot live in `fixtures/projects/`
  (gitlink), `steps.sh`/`update.sh` copy two files only, and
  `GIT_CEILING_DIRECTORIES` must fence the harness from the checkout.
- **M9** `findShortestPath` lacks the `$preferRelative` branch
  `PathDownloader` uses; **M10** the mirror is `ArchivableFilesFinder`
  (VCS dirs at any depth, `.gitattributes export-ignore`, outward
  symlinks, empty dirs — not `vendor/`, not `.gitignore`); **M12**
  `glob()` order is locale-dependent (`LC_ALL=C`), no glob crate does
  `GLOB_BRACE`, `COMPOSER_ROOT_VERSION` overrides the guess when HEADs
  agree; **M13** Windows behaviour undefined; `diff -r` dereferences
  symlinks (compare with `--no-dereference` + a readlink inventory).

Six sub-ports (serialize, a git-like guesser, ArchivableFilesFinder,
brace glob, shortest path variant, harness plumbing for nested repos)
before the first green case: that is a version of its own. **Decision:
v0.8 = Part D only; `path` repositories become v0.9 with these fourteen
points as its opening cadrage; `vcs` after.** The title of this file
keeps "path" for the record; the executed scope is D.
