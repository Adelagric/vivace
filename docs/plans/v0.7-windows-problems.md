# v0.7 — Windows to the end, and Composer's explanations of an unsolvable set

Decided on 2026-09-15, after the merge of #2 (Windows parity on
`windows-latest`, contributed by Luther Monson).

## 1. Scope

### Problem

1. Windows is proven (parity job green) but not deliverable: no Windows
   binary in the release, `install.sh` and the action do not know the
   platform, and `bin-compat` ignores the global `config.json`.
2. `vivacity update` (and `require`/`remove` through it) says
   "Your requirements could not be resolved to an installable set of
   packages (1 problem(s))." and stops. Composer prints the reasons —
   `Problem 1 / - Root composer.json requires … / - x requires y -> found …
   but it conflicts with …` — plus hints. That text is what a user reads to
   fix their `composer.json`; without it vivacity is unusable for exactly
   the case where a tool is needed.

### Constraints

- Byte-identical output with Composer 2.10.3 (`--no-ansi` rendering),
  proven by a differential harness, like everything else.
- Vendored reference + drift mapping for every ported file
  (`harness/drift-reference.sh`).
- No new dependency without a reason in DECISIONS.md.
- Windows binaries only from an already-green Windows CI; no code change
  in the Windows port beyond the global-config gap.

### Non-goals

- `--verbose` variants of the messages (`isVerbose = true`: full version
  lists, repository hints). Ported as a flag but not exercised by the
  harness unless it comes for free.
- `--dry-run`, vcs/path repositories, `bump-after-update` (v0.8).
- The interactive "Did you mean" of `require`.
- A `.msi`/winget/Scoop package: a zip with `vivacity.exe` is enough.
- Colour output. vivacity prints the `--no-ansi` form.

### Alternatives considered

- Messages: a hand-written explanation format ("vivacity's own words").
  Rejected — the user then has two vocabularies for one solver, and
  nothing can be checked against the reference.
- Messages: print Composer's output by delegating unsolvable cases to
  `composer update` (fallback). Rejected — the whole point of the port
  is to not need PHP for `update`; and `require` reverts files on
  failure, which a subprocess cannot coordinate.
- Windows: `install.ps1` separate from `install.sh`. Chosen: yes, a
  PowerShell installer, because `sh` is not a given on Windows and Git
  Bash users can already use `install.sh` once it knows the target.

### Success criteria (observable)

- W1. `release.yml` produces `vivacity-vX-x86_64-pc-windows-msvc.zip`
  (+ `.sha256`) with `vivacity.exe`; `install.ps1` installs it and
  `vivacity --version` prints the tag; `install.sh` under Git Bash/MSYS
  picks the Windows asset.
- W2. `action.yml` works on `windows-latest`: `action-test.yml` gains the
  OS in its matrix, with the same steps (binary input + real Laravel
  install over the network).
- W3. `bin-compat` from `COMPOSER_HOME/config.json` honoured, with the
  precedence env > root composer.json > global config.json > `auto`;
  a unit test per layer.
- P1. On every unsolvable case of the harness, vivacity's stderr from the
  line "Your requirements could not be resolved…" to the end is
  byte-identical to Composer's (`--no-ansi`, `--no-interaction`), exit
  code 2, for `update`, `update <pkg>`, `require` (with revert),
  `remove`, and `update --no-dev` (extra warning line), and the
  dev-extraction failure ("Unable to find a compatible set of packages
  based on your non-dev requirements alone.").
- P2. The corpus of unsolvable cases covers every `Rule` reason
  (`ROOT_REQUIRE`, `FIXED`, `PACKAGE_REQUIRES`, `PACKAGE_CONFLICT`,
  `PACKAGE_SAME_NAME`, `LEARNED`, `PACKAGE_ALIAS`,
  `PACKAGE_INVERSE_ALIAS`, `LOCKED_FILTER_LIST_REMOVED`) and every
  branch of `Problem::getMissingPackageReason` reachable with a
  `composer`-type repository (missing package, wrong stability, platform
  package absent/version, replaced/provided, root require vs temp
  constraint, locked-only, filter-list removed, security-blocked,
  abandoned-blocked, lower-priority repo) — each case named in
  `harness/steps.sh` or the oracle.
- P3. `harness/drift-reference.sh` maps `Problem.php`,
  `SolverProblemsException.php`, `Rule.php` (already) to their ports.

## 2. Plan

### Part W — Windows (small, first: it unblocks users of #2 today)

1. `crates/vivacity-core/src/binproxy.rs`: `resolve_bin_compat` reads
   `COMPOSER_HOME/config.json` → `config.bin-compat` between root and
   default (`layout::global_allow_plugins()` shows the file access;
   factor a `global_config_value(key)` in `layout.rs` used by both).
   Tests: env > root > global > default, invalid value message.
2. `.github/workflows/release.yml`: matrix entry
   `{ os: windows-latest, target: x86_64-pc-windows-msvc }`; the Package
   step branches on the OS: `.zip` (PowerShell `Compress-Archive`) with
   `vivacity.exe`, README, licences; sha256 via `Get-FileHash` written in
   the same `<hash>  <file>` format as `shasum`. The publish job is
   unchanged (globs `artifacts/*`).
3. `install.sh`: `uname -s` `MINGW*|MSYS*|CYGWIN*` → target
   `x86_64-pc-windows-msvc`, asset `.zip`, `unzip`, binary
   `vivacity.exe`; sha256 via `sha256sum` (present in Git Bash).
4. `install.ps1` (new): latest tag via the GitHub API, download the zip
   and its `.sha256`, verify with `Get-FileHash`, install to
   `$env:LOCALAPPDATA\Programs\vivacity` (or `VIVACITY_INSTALL_DIR`),
   print a PATH hint. README "Install" gets the PowerShell one-liner.
5. `action.yml`: the install step already runs `shell: bash` (Git Bash
   on Windows); `install.sh` from step 3 makes it work. `install -m` is
   available in Git Bash. `outputs.version` unchanged. The cache step
   adds `~/AppData/Local/vivacity` and `~/AppData/Local/Composer`.
6. `.github/workflows/action-test.yml`: `windows-latest` in the matrix;
   the Laravel install step is `composer`-free already (network), check
   the boot command works under Windows PHP (`php artisan --version`).
7. Docs: README (platforms line, PowerShell install), `docs/windows.md`
   (installation section), CHANGELOG `[Unreleased]`.

Validation W: CI green on `action-test` (3 OS); a release dry-run is not
possible without a tag — the Package step is exercised on a throwaway
tag `v0.7.0-rc.1`? No: tags are only on the user's word; instead the
Package step is written as a script (`tools/package-release.sh` +
`.ps1`) runnable locally and in `ci.yml`'s Windows job on every push
(builds the zip, verifies the hash, unzips, runs `--version`).

### Part P — Problem messages

Reference files (vendored in `docs/reference/resolver/`): `Problem.php`,
`SolverProblemsException.php`, `Rule.php` (`getPrettyString`,
`getSortableString`… are in `Rule.php`, already vendored),
`Installer.php` (the two catch blocks and the `--no-dev` warning).
Also needed from the phar: `Request::getPresentMap`,
`RepositorySet::getProviders` (Packagist providers API — absent on the
snapshot repos, so the branch yields nothing; kept as a port with a
`None` transport), `Package\Version\VersionParser::formatVersion`? (check),
`Semver\Intervals::compactConstraint` (used by `constraintToText`? check),
`PlatformRepository::isPlatformPackage` (exists).

1. **Oracle first (R0 of this part).** `harness/steps.sh` learns to
   compare stderr: a new case marker `@stderr` makes the harness diff
   the tail of both stderr streams from the first line starting with
   "Your requirements could not be resolved" / "Unable to find a
   compatible set" / "Your lock file does not contain" to the end
   (Composer run with `--no-ansi --no-interaction`, progress lines
   before that point are not compared). Exit codes already compared.
   The comparison is byte-exact. `harness/update.sh` gains the same for
   the plain `update` of `solver-conflict`.
2. **Corpus.** New synthetic registry `fixtures/registry/solver-problems.tar.gz`
   + `fixtures/projects/solver-problems/` (composer.json + a lock), built
   by a documented script (`fixtures/make-solver-problems.sh`, like the
   `solver-policies` one), with packages arranged to hit every reason of
   P2: `acme/a` requiring a missing `acme/nope`; `acme/b` requiring
   `acme/c` at a version that exists only as `-dev` (stability); a
   `conflict` pair; two packages replacing the same name (SAME_NAME);
   an alias chain (`dev-main as 1.0.0`, ALIAS/INVERSE_ALIAS);
   `ext-nope` and `php ^99` (platform present/absent — needs the real
   PHP of the runner, which `steps.sh` already assumes); a locked
   package removed from the registry (locked-only / FIXED); a filter-list
   removed locked package and a security-blocked one (reuse
   `solver-policies` cases with `@stderr`); a case producing a learned
   rule in the problem (backtracking: reuse `solver-backtrack` with a
   constraint tightened to make it unsolvable — LEARNED rules appear
   when `analyzeUnsolvable` reaches a learned rule; the oracle will say
   whether the corpus reaches it, and the harness names the gap if not).
   Each case: one line in `steps.sh`'s table (`@stderr` + command).
   Target: ~30 cases, each named by the reason it exercises.
3. **Port `Rule::getPrettyString`** into
   `crates/vivacity-resolver/src/problem.rs` (new module) — one function
   per reason branch, taking `&Pool`, `&Request` (root requires, fixed
   and locked maps), `installed_map`, `learned_pool`, `is_verbose`.
   `formatPackagesUnique`/`getPackageList` (version condensation
   `condenseVersionList`, `getPlatformPackageVersion`, "as" aliases),
   `constraintToText` (needs `Intervals::compactConstraint`? — verify
   in the reference; if yes the resolver already has `intervals.rs`).
4. **Port `Problem`**: `getPrettyString` (single-reason branches:
   missing package, root requires; multi-reason: sort by
   `getSortableString`/`getRulePriority`, `formatDeduplicatedRules`
   with the "…" collapsing of identical rule texts, learned-rule
   sub-lists), `getMissingPackageReason` (all branches, in the
   reference's order), `getMissingLockedPackageReason`,
   `computeCheckForLowerPrioRepo`, `getProvidersList` (returns
   `None` without a providers API), `isCausedByLock`.
5. **Port `SolverProblemsException::getPrettyString`**: dedup of
   identical problems, numbering, hints (typo/stability, extension hint
   with the exact `--ignore-platform-req` argument list, `-W` hint when
   caused by lock and not `-W`, the two composer-plugin-api hints).
6. **Wire the CLI** (`crates/vivacity/src/lib.rs`, `require.rs`): on
   `SessionErrorKind::Unsolvable`, print `err` + pretty string +
   (`--no-dev`) warning exactly as `Installer::doUpdate`; the
   dev-extraction failure path (`Installer::extractDevPackages`) with its
   two extra lines. `install` from lock (`install_policy_problems`)
   moves to the same `problem.rs` formatting (the P7 partial text is
   replaced, and its steps cases become `@stderr` cases).
   The solver must hand the `Problem`s with their rules and the learned
   pool: `SolveError::Problems` already carries `Vec<Problem>`; add
   `learned_pool` to it.
7. **Drift mapping**: `Problem.php`, `SolverProblemsException.php` →
   `problem.rs`; `Rule.php` gets `problem.rs` as a second twin.
8. Docs: README ("Not ported" list loses the item), HANDOVER (coverage +
   traps), DECISIONS (oracle-by-stderr decision), CHANGELOG.

Validation P: `harness/steps.sh` all cases green including the new
`@stderr` ones; `harness/update.sh` solver-conflict message identical;
CI. Manual golden path: the laravel fixture with `"php": "^99"` added
→ message identical to Composer's.

### Order

W1–W7 (one commit each or two), then P1 (harness) → P2 (corpus, must
show red on every case with the current binary) → P3–P6 (port, cases
turning green one reason at a time) → P7–P8. Meta-analysis by a fresh
subagent before any code; independent review of P3–P6 before merge.
Version 0.7.0 at the end; tag only on the user's word.

## 3. Meta-analysis (adversarial, fresh subagent, 2026-09-15)

Inputs masked (scope without the alternatives + plan). 18 flaws, 11
major, all checked against the reference; every one is accepted. The
corrections below supersede §2 where they conflict.

### Part P

- **M1 (major) `steps.sh` runs the reference with `--quiet`**, and the
  pretty problem is written at NORMAL level (`Installer.php:548-549`):
  compared "as planned", the oracle would only see the headline.
  → `@stderr` cases drop `--quiet` on the reference side, capture stderr
  in its own file (no `2>&1`), and the harness refuses a case whose
  reference tail has no `    - ` reason line ("oracle blind").
- **M2 (major) `GithubActionError::emit`** writes `::error ::…` to
  stdout when `GITHUB_ACTIONS` is set and `COMPOSER_TESTS_ARE_RUNNING`
  is not → green locally, red in CI. → separate stderr (M1) and
  `COMPOSER_TESTS_ARE_RUNNING=1` on the reference side.
- **M3 (major) `SolveError::Problems` holds rule ids into a `RuleSet`
  that is dropped**; `learnedPool` is threaded through the reference but
  never read. → the error carries the problems with their rules
  materialised (owned `Rule`s); no `learned_pool` plumbing.
- **M4 (major) no removed-versions bookkeeping in `Pool`**: every
  version list in the messages merges what the optimizer removed
  (`getRemovedVersions`, `getRemovedVersionsByPackage`), which the Rust
  optimizer explicitly skipped. → port `recordRemovedVersionsForPackage`
  and `applyRemovalsToPool`'s bookkeeping at the exact points of the
  reference (before the early return of `keepPackageInGroup`), keep the
  pool alive until the messages are formatted.
- **M5 (major) the reason branches query the repository set**, not the
  pool: `RepositorySet::findPackages` in its three modes (exact,
  `ALLOW_UNACCEPTABLE_STABILITIES`, `ALLOW_SHADOWED_REPOSITORIES`) over
  the ordered repositories of `Installer::doUpdate` (root package repo,
  platform repo, project repos, lock repo), plus `getRepoName` per
  origin. → port them; `problem.rs` takes a `ProblemContext` built from
  the session (mutable access to the arena).
- **M6 (major) `getProviders` is not only the Packagist API**: every
  repository's loaded packages contribute through their `provide`
  links (`ArrayRepository::getProviders`), platform and root package
  repos included. → port that walk (repository order, dedup by name,
  description cut at 100, `maxProviders + 1` rule); the HTTP
  `providers-api` branch is the only thing left out (DECISIONS).
- **M7 (major) the extension hint lists the php.ini files**
  (`IniHelper::getAll` = `XdebugHandler::getAllIniFiles`, with the
  `COMPOSER_ORIGINAL_INIS` branch and the empty-first-entry rule). → the
  PHP probe returns `php_ini_loaded_file()` and
  `php_ini_scanned_files()`; the helper is ported; the runner's ini
  layout is an oracle assumption named in HANDOVER.
- **M12** corpus claims branches the supported CLI cannot reach:
  temporary constraints (`--with`, refused), a second lower-priority
  repository (harness injects one), the two composer-plugin-api hints
  (they test a 2.0.0 string, dead with `PLUGIN_API_VERSION = 2.9.0`).
  → P2 reworded "every branch reachable with the supported CLI"; those
  three are ported-not-oracled; a generator script
  `fixtures/make-solver-problems.sh` (none exists for `solver-policies`
  — that archive was committed by hand) emits empty `p2/<name>.json`
  + `~dev.json` stubs for every absent name (a missing file is fatal
  over `file://`).
- **M13** `getSortableString` for learned rules is a numeric string and
  PHP 8 `<=>` compares numeric strings numerically. → a
  `php_string_cmp` with the numeric-string rule, unit-tested.
- **M14** `--no-ansi` rendering: strip exactly the registered styles
  (`error`, `warning`, `info`, `comment`, `href=…`, `</>`), keep
  unknown angle-bracket text (`<https://getcomposer.org/…>` is printed
  verbatim); Windows Composer writes `PHP_EOL` — byte parity is a
  Unix-harness claim.
- **M15** `drift-reference.sh` diffs vendored PHP against the phar, it
  knows nothing of Rust ports: P3 is replaced by "every newly ported
  function has its reference vendored (`IniHelper.php`, the
  `XdebugHandler::getAllIniFiles` excerpt with its licence,
  `GithubActionError.php`, `Link.php`) and appears in the HANDOVER port
  map".
- **M18** `Intervals::compactConstraint`/`VersionParser::formatVersion`
  are not used by the three files — dropped from the plan.

### Part W

- **M8 (major) `release.yml`**: the "Version consistency" step is bash
  without `shell:` (fails under pwsh), the artifact glob
  `vivacity-*.tar.gz*` would silently skip a `.zip`, `cp …/vivacity`
  needs `.exe`; a failed Windows leg fails `build` and publishes nothing
  for any platform. → `defaults.run.shell: bash` on the job, the
  packaging in `tools/package-release.sh` (one bash script, all
  targets), artifact glob `vivacity-*`, and `workflow_dispatch` with a
  tag input that runs `build` and skips `publish` — the dry run.
- **M9 (major) `unzip` is not in Git Bash**, and `.sha256` files written
  by PowerShell come out CRLF/UTF-16. → the Windows asset is a `.tar.gz`
  like the others (GNU tar in Git Bash and `C:\Windows\System32\tar.exe`
  both read it); no `.zip`.
- **M10 (major) `action.yml` installs `vivacity` without `.exe`**
  (invisible to pwsh/cmd through PATHEXT; `install -m` fails on the
  `.exe` source), and `action-test.yml` steps are bash-isms without
  `shell:`. → `exe` suffix from `RUNNER_OS`, `defaults.run.shell: bash`
  in `action-test.yml`, `binary:` input with the suffix.
- **M11 (major) `install.sh`/`install.ps1` are never executed by CI**
  (the action test uses `binary:`). → both scripts honour
  `VIVACITY_DOWNLOAD_BASE`; `action-test.yml` packages the local build
  with `tools/package-release.sh`, serves it from a directory
  (`file://`) and runs both installers on the three OSes; "latest" is
  resolved through the `releases/latest` redirect, not the API.
- **M16** `Config` reads `COMPOSER_BIN_COMPAT` with `?:` — `"0"` falls
  through to the config. → same in `resolve_bin_compat`, pinned by a
  test.
- **M17** `install.ps1` execution policy (document `irm … | iex`);
  `uname -m` = `aarch64` on Windows ARM → explicit "unsupported";
  install dir `%LOCALAPPDATA%\Programs\vivacity` on MINGW too, hint
  printed through `cygpath -w`; there is no Windows job in `ci.yml` —
  the package check lives in `windows.yml`, and `windows.yml` runs
  `diff-vendor.sh` only (not `update.sh`/`steps.sh`): resolver parity
  on Windows is not claimed.

### Rejected

Nothing rejected. The `.zip` asset (§2 W2/W3/W4) is withdrawn in favour
of `.tar.gz` (M9); `install.ps1` stays, using `tar.exe` and
`Get-FileHash`.
