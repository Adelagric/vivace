# v0.2 — composer/installers natif, drift CI, GitHub Action

Statut : **exécuté** (2026-09-10) selon r2 — r1 réfuté par un sous-agent frais
(12 failles) ; amendements en fin de document, ils priment sur le corps du
plan. Résultat : oracle installers 665 cas / 0 divergence, fixture wordpress
0 diff projet entier, removal.sh vert, drift.yml + action.yml en place. Niveau de rigueur : **2**
(une disposition de vendor/ fausse chez un utilisateur WordPress/Drupal est le
pire résultat possible pour un outil qui promet l'octet près ; l'émulation
touche cinq modules).

## 1. Cadrage

**Problème.** Tout lock contenant `composer/installers` (WordPress, Drupal,
Magento 1, CakePHP, Grav, ~90 frameworks ; l'un des plugins les plus installés
de Packagist) repart aujourd'hui vers le vrai Composer : vivace n'apporte rien
à ces écosystèmes. Ensuite, la promesse « identique à Composer 2.10.3 » n'a pas
de détecteur : la CI teste `composer:v2` (dernier stable au moment du run) sans
le dire, et rien ne teste le snapshot. Enfin, l'usage en CI — là où vivace sert
— passe par `curl | sh` dans chaque workflow.

**Objectifs (observables).**
1. `vivace install` sur un projet utilisant `composer/installers` produit un
   arbre de projet (vendor/ **et** chemins personnalisés) identique à celui de
   `composer install --no-scripts` avec le plugin actif : `diff -r` sur le
   projet entier = 0 ligne, avec et sans autoloader, sur une fixture WordPress
   figée (wpackagist) ; le boot charge l'autoloader et trouve une classe d'un
   plugin installé hors vendor/.
2. Le calcul de chemin est un port vérifié par oracle : pour une matrice
   (framework × type × nom × installer-paths × installer-name × installer-disable),
   `Installer::getInstallPath` du vrai composer/installers v2.3.0 et le port
   Rust donnent le même chemin — 0 divergence.
3. Ce qui n'est pas porté reste en fallback, nommément : les frameworks dont
   `inflectPackageVars`/`getLocations`/`getInstallPath` sont surchargés
   (CakePHP, Grav, October/Winter, Shopware, Mautic, Bitrix, Oxid,
   SilverStripe, …) → message « installers: package type `x` needs the `y`
   inflection (not emulated yet) », puis exec composer. Jamais de chemin deviné.
4. Un job `drift.yml` (hebdomadaire + manuel) relance le harness contre
   `composer:v2` (dernier stable) et `composer:snapshot` ; en cas d'échec il
   ouvre (ou met à jour) une issue « drift » ; `ci.yml` épingle `composer:2.10.3`
   pour être déterministe.
5. `uses: Adelagric/vivace@vX.Y.Z` installe le binaire vérifié (sha256) dans
   le PATH d'un runner ubuntu/macos ; testé par un workflow qui l'utilise en
   local (`uses: ./`).

**Contraintes.** Pas de PHP exécuté à l'install (règle v1). Sources de
référence vendorées et épinglées (installers v2.3.0 dans
`docs/reference/installers/`, MIT). Table des emplacements **générée** depuis
la source PHP, pas recopiée à la main. Aucune nouvelle dépendance Rust. Le
harness reste le juge ; pas de chiffre de perf nouveau.

**Non-objectifs.** `cweagans/composer-patches`, `oomphinc/composer-installers-extender`,
`drupal/core-composer-scaffold`, `roots/wordpress-core-installer`,
`typo3/cms-composer-installers`, `magento/magento-composer-installer` (chacun est
un plugin distinct ; Drupal complet et Bedrock complet ne passeront **pas**
encore en natif — WordPress « plugins + thèmes via wpackagist » oui). Les
frameworks à inflexion personnalisée (liste générée). Windows. Le résolveur.

**Alternatives écartées.**
- Exécuter le plugin PHP réel pour obtenir les chemins : viole « jamais de PHP »
  et coûte 300 ms, soit le budget entier.
- Recopier les tables à la main : 96 classes, dérive garantie ; un générateur
  PHP + test de drift de la table coûte moins.
- Porter les 40 inflexions personnalisées d'un coup : surface énorme pour des
  frameworks marginaux ; on porte à la demande, le fallback couvre l'attente.
- Action dans un dépôt séparé `setup-vivace` : un dépôt de plus à maintenir et
  à publier ; `action.yml` à la racine de vivace, versionné par les tags de
  release, suffit.

## 2. Analyse de la source (composer/installers v2.3.0)

`Plugin::activate` enregistre un `Installer extends LibraryInstaller` :
- `supports($type)` : `findFrameworkType` = plus long préfixe parmi les clés de
  `$supportedTypes` (krsort → ordre décroissant, donc `fuelphp` avant `fuel`,
  `redaxo5` avant `redaxo`, `concretecms` avant `concrete5`… attention : krsort
  est lexicographique décroissant, pas « plus long d'abord » — à reproduire
  tel quel) ; puis `preg_match('#<fw>-(<loc1>|<loc2>…)#', $type)` — un
  `preg_match` non ancré : `wordpress-plugin-foo` est supporté.
- `getInstallPath` : `BaseInstaller::getInstallPath` → vars `{name, vendor, type}`
  (vendor vide si pas de `/`), `inflectPackageVars` (identité sauf surcharge),
  `extra.installer-name` du paquet remplace `name`, puis `extra.installer-paths`
  de la **racine** : première clé dont la liste contient le nom exact, `type:<type>`
  ou `vendor:<vendor>` → template ; sinon `locations[<type sans préfixe fw>]`
  ou exception. `templatePath` remplace `{$var}` pour `[A-Za-z0-9_]*` (une
  variable inconnue → `$$var` PHP undefined → chaîne vide + warning : à traiter
  comme vide). Le chemin relatif est préfixé de `getcwd()`.
- `installer-disable` (racine) : `true|"all"|"*"` → tout désactivé ; sinon
  liste de clés de frameworks retirées.
- Installed.json / installed.php : `install-path` = `findShortestPath(vendor/composer, chemin)`
  (à confirmer dans FilesystemRepository lors de l'exécution) ; autoload :
  `parseAutoloads` prend `getInstallPath($package)` normalisé ; proxies bin :
  `$installPath/<bin>`.
- Désinstallation : `LibraryInstaller::uninstall` supprime le répertoire
  d'installation (hors vendor/ aussi) — vivace doit retirer un paquet disparu
  du lock à son **ancien** chemin, lu dans installed.json (`install-path`).

Frameworks « table seule » (aucune surcharge) : WordPress, Drupal, Laravel,
Magento, Moodle, ProcessWire (surcharge !), … → la liste exacte est produite
par le générateur, pas devinée ici.

## 3. Plan d'exécution

### Étape A — Référence et table générée (½ j)
- `docs/reference/installers/` : `src/` + `LICENSE` de v2.3.0 (420 Ko).
- `tools/gen-installers-table.php` : pour chaque clé de `$supportedTypes`,
  instancie l'installer avec un paquet factice, dump `getLocations(fw)` et
  marque `custom = true` si `inflectPackageVars`, `getLocations` ou
  `getInstallPath` sont déclarés ailleurs que dans BaseInstaller (réflexion).
  Sortie JSON triée → `crates/vivace-core/src/installers_table.rs` (généré,
  en-tête « ne pas éditer », `pub const FRAMEWORKS: &[Framework]`).
- Test `tests/installers_table_drift.rs` : régénère le JSON via php et compare
  à la table compilée → une mise à jour de la référence sans régénération
  échoue.

### Étape B — Port du calcul de chemin (½ j)
- `crates/vivace-core/src/installers.rs` :
  `find_framework_type`, `supports`, `install_path(pkg, root_extra) -> Result<InstallersPath, Unsupported>`,
  avec `installer-paths`, `installer-name`, `installer-disable`, `templatePath`.
  Unsupported = framework custom, type inconnu, template avec variable inconnue
  (Composer produit une chaîne vide : on refuse plutôt que d'imiter un warning).
- Oracle `tests/oracle_installers.rs` : php charge le phar + les 99 fichiers de
  la référence, construit un Composer via `Factory::create` avec l'extra racine
  du cas, appelle `supports` puis `getInstallPath` sur un `Package` avec type,
  nom, extra ; strip de `getcwd()`. Matrice : tous les frameworks table-seule ×
  tous leurs types × noms {`a/b`, `a/some-name`, `a/CamelCase`, `noslash`} ×
  installer-paths {aucun, par nom, `type:`, `vendor:`, chevauchements, template
  `{$vendor}/{$name}/{$type}`} × installer-name × installer-disable {absent,
  true, "*", [fw]} ; plus des types non supportés (doit refuser des deux côtés)
  et quelques frameworks custom (on vérifie que **nous** refusons, pas le chemin).

### Étape C — Cible d'installation dans tout vivace (1 j)
- `lock.rs` : `install_subpath()` reste (vendor) ; nouveau
  `layout.rs` : `resolve(lock, manifest, with_dev) -> Result<Layout>` avec
  `Layout::target(name) -> &InstallTarget { Vendor(subpath) | Project(rel) }`
  et `Layout::abs(project_root, name)`, `Layout::from_vendor_composer(name)`
  (chemin relatif `findShortestPath(vendor/composer, cible)` pour
  installed.json/php — port de `Filesystem::findShortestPath` déjà dans
  vivace-autoload : à déplacer dans vivace-core `pathutil` et ré-exporter).
  installers actif ssi le lock contient `composer/installers` **et**
  `config.allow-plugins` l'autorise (`true` ou `composer/installers: true`) —
  sinon Composer l'ignore et tout va dans vendor/ (à vérifier à l'oracle :
  comportement de `allow-plugins` absent en non-interactif = erreur Composer →
  fallback).
- `scope.rs` : `composer/installers` sort de LAYOUT ; `analyze` appelle
  `layout::resolve` et remonte `ScopeIssue::InstallersUnsupported(pkg, type, raison)`
  ; `InstallerPaths` ne déclenche plus le fallback si installers est actif
  (sans installers, `installer-paths` est inerte chez Composer aussi → plus un
  motif de fallback, à confirmer par l'oracle).
- `installer.rs` : clone/suppression/bin via `Layout` ; **prune** des paquets
  disparus à l'ancien `install-path` d'installed.json (résolu depuis
  vendor/composer), refus si le chemin sort du projet (`..` au-delà de la
  racine → erreur, jamais de rm hors projet) ; warm-up et store inchangés.
- `state.rs` : `install-path` / `install_path` via `Layout`.
- `binproxy.rs` : cible via `Layout` (le proxy reste dans vendor/bin).
- `vivace-autoload/generator.rs` : `Pkg.install_path` via `Layout`.
- CLI : résumé inchangé ; `VIVACE_TRACE` inclut « layout ».

### Étape D — Fixture WordPress et harness (½ j)

  → prouve que l'autoloader pointe hors vendor/.

### Points de validation
- A : table générée = JSON du php (test drift vert) ; nombre de frameworks
  table-seule affiché.
- B : oracle installers 0 divergence sur la matrice ; clippy/fmt/tests.
- C : les 4 fixtures actuelles restent à 0 diff (aucune n'a installers → rien
  ne doit bouger) ; un lock synthétique avec installers non autorisé → vendor/.
- D : fixture wordpress 0 diff projet entier, ±autoloader, froid/chaud ; boot
  trouve la classe hors vendor/ ; suppression d'un plugin du lock → répertoire
  hors vendor/ retiré (test dédié dans le harness ou test d'intégration Rust).
- E/F : workflows verts sur GitHub (drift déclenché à la main une fois).

### Risques identifiés dès le plan
- Chemins avec `/` final dans les templates : normalisation Composer à
  reproduire exactement dans `install-path` (diff dira).
- `preg_match` non ancré dans `supports` : types exotiques acceptés par
  Composer ; notre port doit accepter pareil (oracle inclut `wordpress-plugin-x`).
- Un `installer-paths` peut cibler **vendor/** lui-même ou un chemin absolu ;
  absolu → refus (fallback), vendor/… → traité comme Project(rel) tel quel.
- Un chemin cible partagé par deux paquets (`config/sync/` Drupal `config`) :
  Composer écrase ; on refuse (deux paquets → même cible = Unsupported).
- Suppression hors vendor/ : périmètre strict au projet ; chemin de l'ancien
  installed.json seulement.

## 4. Amendements r2 (après méta-analyse)

Failles retenues et réponses (numérotation de la méta) :

1. **Version verrouillée de composer/installers — gating obligatoire.** La
   logique (Installer/BaseInstaller/Plugin) est identique sur tout 2.x
   (vérifié par diff 2.0.0→2.3.0 : seules des entrées de table s'ajoutent),
   mais les tables changent (moodle 2.1.0/2.3.0, drupal `recipe` 2.3.0,
   frameworks ajoutés). Décision : une table JSON **par tag** 2.0.0…2.3.0
   générée par `tools/gen-installers-table.php <phar> <src>` dans
   `crates/vivace-core/assets/installers/<tag>.json` (include_str! + parse
   paresseux) ; `layout::resolve` prend la table du tag verrouillé exact ;
   1.x ou tag inconnu → `InstallersUnsupported("composer/installers X: not a
   ported version")`. Test de drift : régénération à partir de
   docs/reference/installers (2.3.0) = asset 2.3.0. Les sources des autres
   tags ne sont pas vendorées (seules leurs tables le sont, générées une fois
   et datées dans l'en-tête du JSON).
2. **Fixture WordPress** : wpackagist n'a ni autoload ni mu-plugins. Ajout de
   `roots/soil` (Packagist, MIT, `wordpress-plugin`, PSR-4 `Roots\Soil\`) pour
   le boot `class_exists`, d'un mu-plugin via `repositories: [{type: package}]`
   (zip wp.org d'un plugin, retypé `wordpress-muplugin`, avec un `bin` pour
   exercer les proxies hors vendor/ — faille 12). Plugins pérennes (akismet,
   hello-dolly) pour limiter les disparitions de zips ; make.sh les met dans le
   cache Composer partagé par les deux côtés du harness.
3. **extract.rs** : strip du premier composant ssi l'archive a exactement une
   entrée de premier niveau et que c'est un répertoire (`ArchiveDownloader`,
   `.DS_Store` de premier niveau ignoré) ; sinon aucune entrée n'est perdue.
   Test unitaire (zip mono-dossier, multi-racine, fichier racine + dossier).
   Corrigé **avant** le reste (bug indépendant, préexistant).
4. **Oracle unique de bout en bout** : php construit Composer via
   `Factory::create` avec le composer.json du cas, active le plugin
   (`Plugin::activate`) et interroge `InstallationManager::getInstallPath`
   (dispatch réel : `supports` faux → LibraryInstaller → vendor/), puis
   `Filesystem::findShortestPath("$cwd/vendor/composer", $path, true)`. Le
   port Rust doit rendre (chemin relatif au projet, install-path) identiques.
   Conséquence : `supports` faux (type hors regex, `installer-disable`) n'est
   pas « Unsupported » mais **vendor/**. `find_shortest_path` devient un port
   exact de `Filesystem::findShortestPath` (déplacé dans vivace-core, oraclé
   par la même matrice) ; `state.rs::relative_install_path` disparaît.
5. **Désinstallation** : Composer recalcule `getInstallPath` avec la config
   courante, il ne lit pas installed.json. Règle vivace : un paquet à retirer
   est effacé au chemin calculé par le layout courant pour (nom, type, extra)
   lus dans installed.json, **ssi** ce chemin est égal à son ancien
   `install-path` ; désaccord → fallback (Composer gère mal ce cas, on ne
   l'imite pas). Le prune du parent vide (`dirname`) s'applique à toute cible
   avec `/` dans le nom, plus seulement `vendor/<ns>`. Toute suppression reste
   confinée au projet (chemin canonique sous la racine).
6. **Action** : `version` par défaut = `github.action_ref` (jamais
   `releases/latest` depuis une action) ; `install.sh` envoie
   `Authorization: Bearer $GITHUB_TOKEN` s'il est présent ; input `binary`
   pour tester la PR elle-même (`cargo build --release` puis `uses: ./`).
   L'attestation de provenance est notée comme suite possible, hors v0.2 ; le
   README dit « sha256-verified download », pas « verified binary ».
7. **allow-plugins** : `true`/`false` global, objet à motifs
   (`packageNameToRegexp` : `*` → `.*`), héritage de `$COMPOSER_HOME/config.json`
   (lu, même parseur) ; installers en `packages-dev` avec `--no-dev` → plugin
   absent → vendor/. Absent partout → fallback (Composer échoue en non
   interactif).
8. **installer-paths / installer-name** : schéma strict
   `object<string, string|string[]>` avec chaînes non vides, sinon
   `Unsupported` ; `installer-name` chaîne non vide ≠ "0" (sémantique
   `!empty`), sans `/` ni `..` ; variable de template inconnue → `Unsupported`.
   Le générateur marque déjà `custom` pour `templatePath` et
   `mapCustomInstallPaths` surchargés.
9. **Cibles refusées** (→ fallback nommé) : racine du projet, sous vendor/,
   hors projet, absolue, deux paquets sur la même cible, cible préfixe ou
   suffixe d'une autre cible.
10. **Drift à deux étages** : (1) extraction des jumeaux de docs/reference/
    depuis le phar `composer:v2` / `snapshot` et `diff` fichier par fichier —
    signal nominatif en secondes ; (2) `cargo test` + make.sh + harness.
    `gh label create drift -f`, `permissions: issues: write`, version de
    Composer dans la clé de cache des fixtures.
11. **Dists wp.org** : pas de `reference` ni `shasum`, `source` svn — ces
    chemins sont exercés par la fixture (identité de store sans ref, référence
    installed.php = `source.reference`).
12. **Proxies bin hors vendor/** : `binproxy.rs` calcule `findShortestPath`
    (port exact) au lieu de `../` codé en dur ; cas dans la fixture (mu-plugin
    avec `bin`) et dans `fixtures_binproxy.rs`.

Réponse à la solution alternative de la méta : « Layout = une passe unique
produisant `BTreeMap<name, chemin relatif au projet>` et une seule fonction
`install_dir(name)` » — adoptée telle quelle (c'est plus simple que l'enum
`InstallTarget` de r1). Le drift en deux étages est adopté. L'oracle unique
est adopté.

Ordre d'exécution r2 : 3 (extract) → 1+A (tables par tag) → B (port +
oracle unique, findShortestPath exact) → C (layout, prune) → D (fixture,
harness) → E (drift) → F (action) → G (docs, 0.2.0).

## 5. Revue indépendante (sous-agent, 2026-09-11)

Quatre majeurs, tous corrigés avant commit : (1) `--working-dir` relatif →
proxies bin à chemin absolu (racine absolutisée dans la CLI, `installer.rs`
lit `layout.root()`) ; (2) `--no-plugins` ignoré par le layout (transmis,
install et dump-autoload) ; (3) état du plugin décidé sur le lock seul alors
que Composer le charge depuis installed.json → règle de transition (présent
d'un seul côté + paquet concerné → fallback) ; (4) suppression d'un paquet à
`target-dir` laissait `vendor/<ns>` (répertoire effacé = `vendor/<name>`).
Mineurs corrigés : `.DS_Store` de premier niveau (déplacé comme Composer),
`installer-disable` objet JSON, garde contre la boucle infinie de
`common_path` sur chemins relatifs, `{` refusé dans `installer-name`,
`removal.sh` (contrôle vendor/ vide de sens retiré), pipe `grep -q` de
`action-test.yml`, jumeaux Filesystem/PluginManager/ArchiveDownloader/
LibraryInstaller vendorés et surveillés par le drift, fixture wordpress dans
`fixtures_scope`, README (2.0.0–2.3.0). Non corrigés (documentés dans
HANDOVER) : `realpath()` de BinaryInstaller sur vendor/ symlinké, `///a` dans
normalizePath, copie du phar oracle non rafraîchie dans temp_dir.
